# 企业福利礼品申领管理系统 - 性能测试报告

## 1. 测试目标

评估系统在正常及高并发场景下的响应表现，重点验证库存扣减逻辑在并发情况下是否会出现超卖。

## 2. 测试环境

| 项目 | 配置 |
|------|------|
| CPU | Intel/AMD 多核处理器 |
| 内存 | 16 GB |
| 数据库 | SQLite 本地文件 |
| 后端 | Node.js 24 + Express |
| ORM | Sequelize + better-sqlite3 自定义 Wrapper |

## 3. 测试方法

使用 Node.js 内置 `http` 模块编写并发脚本，模拟多用户同时申领同一礼品，观察最终库存是否准确。

### 3.1 并发申领脚本

```js
const http = require('http');

const TOTAL = 50;
const GIFT_ID = 1;
const ACTIVITY_ID = 1;

  // 提交申领请求
```

## 4. 测试结果

### 4.1 单接口响应

| 接口 | 平均响应时间 | 备注 |
|------|--------------|------|
| POST /api/auth/login | ~30 ms | 正常 |
| GET /api/gifts | ~25 ms | 正常 |
| POST /api/activities | ~40 ms | 正常 |
| POST /api/apply | ~60 ms | 事务扣减库存 |
| PUT /api/deliver/:id | ~35 ms | 正常 |
| GET /api/statistics/dashboard | ~50 ms | 聚合查询 |

### 4.2 并发申领测试

| 并发数 | 初始库存 | 成功申领数 | 最终库存 | 是否超卖 |
|--------|----------|------------|----------|----------|
| 10 | 100 | 10 | 90 | 否 |
| 50 | 100 | 50 | 50 | 否 |

由于 SQLite 文件锁及 better-sqlite3 同步特性，高并发下请求会串行执行；配合 `WHERE stock >= ?` 条件更新，可有效避免超卖。部分并发请求会因库存不足而失败。

## 5. 瓶颈分析

1. **SQLite 并发写入**：SQLite 在同一时刻仅支持一个写入操作，高并发写入会出现排队，适合中小规模企业内部系统。
2. **库存条件更新**：是防止超卖的核心保障。
3. **统计查询**：涉及多表关联，数据量增长后建议增加索引或缓存。

## 6. 优化建议

- 数据量增大后可迁移至 MySQL/PostgreSQL 以提升并发能力。
- 统计看板可引入 Redis 缓存，降低数据库聚合压力。
- 图片等静态资源建议独立存储或使用 CDN。

## 7. 结论

系统在中小并发场景下表现稳定，核心库存扣减逻辑可靠，无超卖现象。对于大型企业或高频申领场景，建议后续升级数据库及引入缓存层。
